## Context

The owner of flakeyard requires that logic with at least two users lives in one
reusable place, also when the users are in different repositories.
[FY-0035][fy-0035] makes this an organization rule. Its scope is logic: scripts,
`jq` programs, Nix modules, test helpers and stubs. The thin callers
(`test.yaml`, `scorecard.yaml`, `release.yaml`), `renovate.json`, `REUSE.toml`
and the license are generated by the templates of [FY-0022][fy-0022] and are out
of scope. For shell code that runs on runners without Nix, [FY-0035][fy-0035]
chooses a library action, this repository, and amends [FY-0003][fy-0003],
[FY-0022][fy-0022], [FY-0024][fy-0024] and [FY-0030][fy-0030] for it.

Until then, every action and workflow carried its own copy of such code, since
an action of [FY-0030][fy-0030] has one task and no imports from other
repositories. On `main` of each repository on 2026-11-07 the copies are:

- Annotations and the job summary: `.github/actions/lib/report.sh` of
  workflow-check (53 lines) and of workflow-release (40), and
  `scripts/lib/report.sh` of action-flake-lock (103). Only workflow-check and
  action-flake-lock escape messages; only action-flake-lock escapes properties
  and caps annotations with a line that says how many more the summary has.
- Calls of the GitHub API: `.github/actions/lib/github/api.sh` of workflow-check
  (84) and of workflow-release (50), and `scripts/lib/api.sh` of
  action-flake-lock (48). workflow-check and action-flake-lock retry transient
  errors, only action-flake-lock also a GraphQL `RATE_LIMITED`, and
  workflow-check and workflow-release return `NOT_FOUND` for HTTP 404.
- Files through the contents API: `.github/actions/lib/github/contents.sh` of
  workflow-check (34; `file_at`, `root_files`) and of workflow-release (20;
  `file_at`, `find_file_at`).
- Repository names: `REPOSITORY_FORM` in
  `.github/actions/lib/github/repository.sh` of workflow-check (7) and the same
  rule as `REPOSITORY_NAME_FORM` in `scripts/lib/forms.sh` of action-flake-lock;
  lists of `owner/repo` are checked and searched inline in two actions of
  workflow-check.
- Steps with a clean environment: `scripts/run-step.sh` of action-setup-nix and
  of action-flake-lock (39 lines each), which differ only in their list of
  allowed variables and a comment.
- Time: `.github/actions/lib/clock.sh` of workflow-release (12), which reads a
  `NOW` that only tests set.
- Test harnesses: `tests/lib/case.sh` and `tests/lib/checks.sh` of
  workflow-check (64 and 84), workflow-release (61 and 55) and action-flake-lock
  (88 and 71), `tests/harness/case.sh` of action-setup-nix (60), `tests/lib.sh`
  of `.github` (84), `tests/unit/lib.sh` of renovate-config (96) and of
  image-devcontainer (142), and `tests/lib/case.sh` of workflow-scorecard (24).
- Stubs: `tests/bin/gh` of workflow-check (124), workflow-release (113),
  action-flake-lock (86), `.github` (79) and image-devcontainer (62), each with
  its own fixture format, and `tests/bin/nix` of workflow-check (91),
  action-flake-lock (36) and image-devcontainer (49).

`scripts/check/eol.sh` (60 lines) is the same file in five repositories;
[FY-0036][fy-0036] removes it rather than moving it here. The duplicated Nix
modules stay until the atoms that own them are released ([FY-0035][fy-0035]).

A probe on 2026-11-07 tested how an action can expose its directory:

- A composite action without steps whose output is `${{ github.action_path }}`
  runs, but the output is empty on Linux, macOS and Windows runners and in a
  container job.
- One step with `shell: /usr/bin/bash --noprofile --norc -p -e {0}` that writes
  `path=$ACTION_DIR` to `$GITHUB_OUTPUT`, with `ACTION_DIR` set from
  `${{ github.action_path }}` in `env`, works on `ubuntu-24.04` and
  `ubuntu-24.04-arm`, through a nested composite action, in a container job and
  with a fake `bash` first on `PATH` and a `BASH_ENV` set through `$GITHUB_ENV`.
  The path has the form `/home/runner/work/_actions/flakeyard/<repo>/<sha>`.
- macOS and Windows runners have no `/usr/bin/bash`.

## Decision

### Product

action-shell-lib is a composite action whose one task is to expose its
directory. It has no inputs and one output, `path`. It has two steps: the path
step, which runs on the runners the library supports and sets `path`, and the
rejection step, which runs on every other runner and fails. A supported runner
is a GitHub-hosted Linux runner on X64 or ARM64; the path step runs on exactly
these, and the rejection step on exactly the rest:

```yaml
- id: path
  if: >-
    ${{ always() && runner.os == 'Linux'
        && runner.environment == 'github-hosted'
        && (runner.arch == 'X64' || runner.arch == 'ARM64') }}
  shell: /usr/bin/bash --noprofile --norc -p -e {0}
  env:
    ACTION_DIR: ${{ github.action_path }}
  run: printf 'path=%s\n' "$ACTION_DIR" >>"$GITHUB_OUTPUT"
- if: >-
    ${{ always() && !(runner.os == 'Linux'
          && runner.environment == 'github-hosted'
          && (runner.arch == 'X64' || runner.arch == 'ARM64')) }}
  shell: bash
  run: |
    echo "::error::Unsupported runner $RUNNER_OS/$RUNNER_ARCH" \
      "($RUNNER_ENVIRONMENT): use a GitHub-hosted Linux runner on X64 or" \
      "ARM64, such as ubuntu-24.04 or ubuntu-24.04-arm."
    exit 1
```

Both conditions start with `always()`. A condition without a status function
holds only while the job succeeds, so in a job that goes on after a failure or a
cancellation, such as one that posts a commit status, both steps would be
skipped and `path` would be empty. With `always()`, the action gives `path` or
fails whenever it runs; a consumer step that runs on `always()` gives the
library step `if: always()` too.

The rejection step uses the `bash` of the runner, since macOS and Windows
runners have no `/usr/bin/bash`, and reads only `RUNNER_OS`, `RUNNER_ARCH` and
`RUNNER_ENVIRONMENT`, which the runner sets. The text of the rejection lives in
the library, so a consumer keeps no runner checks of its own: the library fails
the job on an unsupported runner before any step that sources it.

A consumer calls it with an `id`, pinned as
`uses: flakeyard/action-shell-lib@<sha> # vX.Y.Z`, passes the output to its
steps as the environment variable `SHELL_LIB` and sources the modules it needs
from there.

### Modules

The library holds shell files that are sourced, and one that is run:

- `report.sh`: workflow commands and the job summary. `escape_command` and
  `escape_property` escape messages (`%`, CR, LF) and properties (also `,` and
  `:`). `error`, `warning` and `notice`, each `MESSAGE [FILE [TITLE]]`, write
  annotations with a cap of 10 per kind and step, the last of which says how
  many more of that kind there are, as GitHub keeps at most 10 of each kind per
  step ([action-flake-lock ADR-0002][afl-0002]); `flush [WHERE]` writes that
  last annotation as the step ends. `problem` reports an error and goes on, and
  `has_problems` tells whether it was called; `fail` reports an error, flushes
  and exits. `summary` and `code_span` write the job summary.
- `github/api.sh`: `NOT_FOUND`; `api_request METHOD PATH [ARG...]`, which
  retries only requests that change nothing (GET, HEAD and GraphQL queries) and
  only on server errors, HTTP 429, lost connections and GraphQL `RATE_LIMITED`,
  with a growing delay and a bounded number of attempts, and returns `NOT_FOUND`
  for HTTP 404; `api_get`.
- `github/contents.sh`: `file_at`, a file of a repository at a commit through
  the contents API.
- `github/forms.sh`: `REPOSITORY_NAME_FORM`, `REPOSITORY_FORM` and `TOKEN_FORM`,
  the forms of names of repositories and of tokens, and `is_repository_list` and
  `lists_repository` for lists of repositories as JSON.
- `env.sh`: `SYSTEM_PATH`, the tools of the runner, and `step_environment`,
  which keeps the `PATH` of the job in `JOB_PATH` and sets `PATH`, `LC_ALL=C`
  and `inherit_errexit` for the script of a step.
- `run-step.sh STEP_DIR STEP [VARIABLE...]`: runs one script of a consumer step
  in a clean environment (see below).
- `internal/testing/`: the harness of test cases and checks, stubs of `gh`,
  `date` and `sleep`, with one fixture format for the `gh` stub, and helpers for
  fixtures. It is not public API.

Names of functions, constants and variables that are not public API start with
`_`. The README documents the exact list of public names.

### Rules of the API

1. A function, constant or script enters the library only when at least two
   places use it, in one repository or in different ones, or when another
   function of the library needs it. Logic with one user stays with its user;
   posting a commit status, for example, stays in workflow-check.
2. Where copies differ, the library keeps one behaviour that is safe for every
   user: the escaping and the cap of action-flake-lock, the retries of
   action-flake-lock and the `NOT_FOUND` of workflow-check. A consumer adapts to
   it in the pull request that adopts the library, and that pull request deletes
   its copy.
3. A sourced module defines only functions and read-only constants. It sets no
   shell options, traps or `PATH`, runs no command and writes no file when it is
   sourced, and sourcing it twice is harmless.
4. A function reads and writes only the variables its documentation names, keeps
   everything else `local`, prints results on stdout and diagnostics on stderr
   or as annotations, and documents its return codes.
5. Text that others choose reaches workflow commands only through
   `escape_command` and `escape_property`, and `jq` only through `--arg` or
   `--argjson`.
6. No variable exists only to let tests change behaviour. Tests change time and
   waiting through the stubs of `internal/testing/` on `PATH`: the delays of
   retries with the `sleep` stub, the date with the `date` stub.

### run-step.sh

```sh
/usr/bin/bash -p "$SHELL_LIB/run-step.sh" STEP_DIR STEP [VARIABLE...]
```

The consumer names, in the `run` line of its `action.yml`, the directory of its
step scripts, the step and every variable the step may see; the library adds
only `SHELL_LIB`. Before it runs anything, `run-step.sh` checks that `SHELL_LIB`
and `STEP_DIR` are absolute, have no `..` component and are directories, and
that `STEP` matches `^[a-z-]+$`. It then runs `STEP_DIR/STEP.sh` with
`/usr/bin/env -i` and `/usr/bin/bash -p`, so that exported functions,
`SHELLOPTS`, `BASHOPTS`, `PS4` and `BASH_ENV` set by earlier steps of the job do
not reach it.

### Requirements

- GitHub-hosted Linux runners on x86_64 and arm64, with `/usr/bin/bash` 5.2 or
  later, the version of Ubuntu 24.04.
- The modules run only coreutils, `grep`, `sed`, `gh` and `jq`, found on the
  `PATH` that the calling step sets; the library installs and builds nothing.
  API steps use the `gh` and `jq` of the runner under the API exception of
  [FY-0030][fy-0030]; action-flake-lock gives its steps the `gh` and `jq` pinned
  in its own flake.

### Versioning

The public API, documented in the README, is the output `path`, the paths of the
modules, and for each function, constant and script its name, arguments, output,
return codes and the variables it reads and writes ([FY-0024][fy-0024]).
Removing or changing any of them is a major release, adding one a minor release;
before 1.0 a 0.y release plays the role of a major one. `internal/testing/` is
excluded. A major release of the library is not by itself a major release of a
consumer: the consumer's own API decides that.

Every `uses:` of the library in one repository names the same commit, in its
`action.yml` or its workflows. The tests of a consumer MAY fetch the library's
source at that commit and take the commit from the file that pins it, the
`action.yml` or a workflow ([FY-0003][fy-0003] as amended by
[FY-0035][fy-0035]); this is not a second way to deliver it. A repository that
uses the library only in its tests pins it in the job of its CI workflow that
runs those tests.

### Release order

action-shell-lib is released before workflow-release and action-setup-nix use
it; its own first release runs on a workflow-release that does not use it yet
([FY-0022][fy-0022] as amended by [FY-0035][fy-0035]). A change of the library
is released in this order: action-shell-lib, then action-setup-nix and
action-flake-lock, then workflow-release and workflow-check, each in one pull
request that updates all of these pins it has; workflow-check also pins
action-setup-nix and action-flake-lock. Renovate proposes updates of
`flakeyard/action-shell-lib` with commit type `fix` in every consumer, by a rule
that renovate-config adds.

### Threat model

The library runs inside sensitive jobs: the job of workflow-release that holds
the private key of the release bot, and action-setup-nix, which uses `sudo`.
Code of the library therefore has the power of the job that sources it. It is
released behind the release gate of [FY-0030][fy-0030] and covered by the
release audit of [FY-0033][fy-0033] like every flakeyard release, and consumers
reach only the commit they pin. Repositories that allowlist actions add
`flakeyard/action-shell-lib`. The library makes no request that a consumer does
not ask for, never reads or prints a token itself (`gh` takes it from the
environment that the consumer sets), and writes to `$GITHUB_OUTPUT` only in its
path step and never to `$GITHUB_ENV` or `$GITHUB_PATH`. `run-step.sh` does not
cover variables of the dynamic loader, such as `LD_PRELOAD`: the loader reads
them when the first bash of the step starts, before the library.

### CI of this repository

This repository is checked by workflow-check. Until atom-shell is released it
has no flake, `flake: ""`, and shellcheck and shfmt run locally; it does not add
another copy of the Nix modules that [FY-0035][fy-0035] lets stay elsewhere.
Every module has tests that use `internal/testing/` of this repository.
`test.yaml` has, next to workflow-check, a job `unit` that runs `tests/run.sh`
with the `bash` of the runner, and a job `action` that runs the action itself on
`ubuntu-24.04` and `ubuntu-24.04-arm` and checks that `path` names a directory
with `run-step.sh`. CI runs no jobs on macOS or Windows runners, by a rule of
the owner, since such jobs of GitHub often wait for a runner or fail for reasons
of their own; a static test of `action.yml` in `tests/run.sh` checks instead
that the conditions of the two steps are exact complements under every status of
the job and that the rejection step fails.

## Constraints

### Action

- The action MUST have no inputs and exactly one output, `path`.
- It MUST have exactly two steps. The path step MUST run only on GitHub-hosted
  Linux runners on X64 or ARM64, with
  `shell: /usr/bin/bash --noprofile --norc -p -e {0}`, and MUST only write
  `path=<directory of the action>` to `$GITHUB_OUTPUT`. The rejection step MUST
  run on exactly every other runner, with `shell: bash`, and MUST only write an
  error annotation that names the runner and exit 1.
- Both conditions MUST start with `always() &&`, so that one of the steps runs
  whenever the action runs, also after a failure or a cancellation of the job.
- `${{ github.action_path }}` MUST reach the path step only through `env`, never
  inside `run:`.
- The text of the rejection MUST live in the library; consumers MUST NOT keep
  runner checks of their own.

### Contents

- A function, constant or script MUST NOT enter the library unless at least two
  places use it or another function of the library needs it.
- A consumer's pull request that adopts a module MUST delete its own copy of
  that logic.
- A sourced module MUST define only functions and read-only constants, MUST NOT
  set shell options, traps or `PATH`, MUST NOT run commands or write files when
  sourced, and MUST be harmless to source twice.
- A function MUST read and write only the variables its documentation names.
- Messages of workflow commands MUST be escaped with `escape_command` and
  properties with `escape_property`.
- `report.sh` MUST write at most 10 annotations of each kind per step, counting
  the last one, which names how many more of that kind the job summary has.
- `api_request` MUST retry only transient errors, a bounded number of times, and
  MUST return `NOT_FOUND` for HTTP 404.
- Modules MUST run no tools other than bash builtins, coreutils, `grep`, `sed`,
  `gh` and `jq`, and MUST NOT install or build tools.
- Modules MUST NOT read the time other than through `date`, MUST NOT wait other
  than through `sleep`, and MUST NOT read a variable that exists only for tests.
- Names that are not public API MUST start with `_`.

### Clean environment of steps

- The variables a step may see MUST be the arguments of `run-step.sh` in the
  consumer's `action.yml`; `run-step.sh` MUST add only `SHELL_LIB`.
- `run-step.sh` MUST fail before it runs anything when `SHELL_LIB` or `STEP_DIR`
  is not absolute, has a `..` component or is not a directory, or when `STEP`
  does not match `^[a-z-]+$`.
- `run-step.sh` MUST run the step with `/usr/bin/env -i` and `/usr/bin/bash -p`.

### Interface and versioning

- The README MUST document every public function, constant and script with its
  arguments, output, return codes and the variables it reads and writes.
- Removing or changing any of them, the paths of the modules or the output
  `path` MUST be a major release; before 1.0, a 0.y release.
- `internal/testing/` MUST NOT be public API, and only tests MAY use it, fetched
  at the commit that the consumer pins.
- Every `uses:` of the library in one repository MUST name the same commit.
  Tests MUST take that commit from the file that pins it, the `action.yml` or a
  workflow; a repository that uses the library only in tests MUST pin it in the
  job of its CI workflow that runs them.
- The library MUST support GitHub-hosted Linux runners on x86_64 and arm64 with
  `/usr/bin/bash` 5.2, and MUST NOT need features of a newer bash.

### Security

- The library MUST NOT make requests that a consumer does not ask for, MUST NOT
  read or print tokens itself, and MUST NOT write to `$GITHUB_ENV` or
  `$GITHUB_PATH`.
- Releases MUST pass the release gate of [FY-0030][fy-0030] and the audit of
  [FY-0033][fy-0033].

### Test suite

- Every module MUST have tests, and they MUST use `internal/testing/` of this
  repository.
- CI MUST run `tests/run.sh` in a job `unit` with the `bash` of the runner.
- CI MUST run the action on `ubuntu-24.04` and `ubuntu-24.04-arm` and check that
  `path` is a directory that contains `run-step.sh`. It MUST NOT run jobs on
  macOS or Windows runners; a static test of `action.yml` MUST check that the
  conditions of the two steps are exact complements under every status of the
  job and that the rejection step fails.
- The repository MUST NOT add a copy of a Nix module that another repository
  has; its checks come from released atoms.

## Consequences

- (+) A fix of escaping, retries or the clean environment is made once and
  reaches every consumer with one update of a pin.
- (+) Consumers get the strictest of the diverged behaviours: escaped
  properties, capped annotations and retried GraphQL rate limits everywhere.
- (+) The variables of each step stay visible in the consumer's `action.yml`,
  where a review of the consumer sees them.
- (+) One harness and one fixture format for the `gh` stub serve every
  repository's tests.
- (+) Consumers keep no runner checks of their own; the library gives the same
  error on every unsupported runner.
- (−) A compromised release of the library reaches every job that uses it,
  including the job with the key of the release bot; only the pins, the release
  gate and the release audit stand in the way.
- (−) A change of the library needs a chain of releases before workflow-check
  and workflow-release carry it.
- (−) Each consumer job spends one more step, and needs the library before any
  step that sources it.
- (−) Until atom-shell is released, shellcheck and shfmt of this repository run
  only locally.
- (±) A major release of the library does not force a major release of its
  consumers, so their changelogs show the update as a fix.

## Alternatives considered

- **Generated vendored copies.** Each consumer keeps a copy kept equal by a
  generator. The code is still duplicated, and the hosted Renovate of
  [FY-0029][fy-0029] cannot regenerate the copies when the source changes.
- **A composite action without steps.** Simplest, but the probe showed that its
  `path` output is empty.
- **A library that runs scripts, `with: script`.** The library would run the
  consumer's code, and every input, variable and output of the step would have
  to be passed through it.
- **An exception for action-setup-nix.** Keeps its copies because it runs with
  `sudo`. Rejected by the owner rule; the hardened step works in its jobs as
  well.
- **Doing nothing.** Leaves the copies above to diverge further, while only some
  of them escape annotation properties or retry rate limits.
